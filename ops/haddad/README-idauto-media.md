# IDauto photographs — the Haddad copy (Update 3.1)

`idauto-media-receiver.js` keeps a second copy of every IDauto photograph on Haddad, by SHA-256.
idauto.tn (the VPS) stays the primary copy — the one in the nightly off-host backup — and sends each new
file here through `reference/replica/haddad-replica.js` (retried every 30 s; a failure is recorded and shown).

Install on Haddad (user service, nothing as root):

```
install -d -m 700 ~/.config/idauto-media /srv/hybrid/idauto-media
# ~/.config/idauto-media/receiver.env (mode 0600):
#   IDAUTO_MEDIA_RECEIVER_TOKEN=<32+ random characters, the same value as IDAUTO_HADDAD_MEDIA_TOKEN on the VPS>
#   IDAUTO_MEDIA_RECEIVER_ROOT=/srv/hybrid/idauto-media
#   IDAUTO_MEDIA_RECEIVER_PORT=8853
systemctl --user enable --now idauto-media-receiver     # unit: ExecStart=/usr/bin/node <repo>/ops/haddad/idauto-media-receiver.js
tailscale serve --bg --set-path /idauto-media http://127.0.0.1:8853   # private network only
```

On the VPS, in the idauto-api environment file: `IDAUTO_HADDAD_MEDIA_URL=https://<haddad tailnet name>/idauto-media`,
`IDAUTO_HADDAD_MEDIA_ADDR=<haddad tailnet address>` (the VPS does not resolve the tailnet name),
`IDAUTO_HADDAD_MEDIA_TOKEN=<the token>`.

`/srv/hybrid` is not covered by the VPS backup; the Haddad copy is a second copy, not the backup.

## Update 4 — the monthly archive and LENS

The receiver also files every photograph and carte grise in a monthly tree, without moving or copying anything:

```
/srv/hybrid/idauto-media/
├── ab/cd/<sha256>                                   the stored file (content-addressed, unchanged since 3.1)
├── 2026/11/vehicle-photos/20261118T080910Z_<sha16>.jpg        hard link to the same file (same inode, same bytes)
├── 2026/11/vehicle-photos/20261118T080910Z_<sha16>.jpg.json   its metadata
├── 2026/11/carte-grise/…
├── 2027/01/…
└── .archive-index/<sha256>.<category>.json          where each file was filed (keeps the place stable)
```

- The month is the month of the **upload** (UTC), which is always known; the capture date is in the `.json`.
- The `.json` holds: SHA-256, category, upload and capture dates, GPS (device or EXIF, never an IP address) and its
  source, place name, MIME type, original filename, source (public scanner / workshop / admin), uploader, vehicle IVID
  and VIN when known, record id and version. It is rewritten when the record changes (correction, attachment); the
  file never is.
- `DELETE /objects/<sha>` removes the file, its monthly entry and its `.json`.
- Files 0600, folders 0700. Every path piece is generated by the receiver from validated values (fixed categories,
  dates, hex digits): nothing from a request becomes a path.

LENS (optional, carte grise only): add to `receiver.env`

```
IDAUTO_LENS_URL=http://127.0.0.1:8830                         # loopback only — LENS is never exposed beyond Haddad
IDAUTO_LENS_TOKEN_FILE=/home/othman/.local/share/mythos-lens/api.token
```

A carte grise is then submitted to LENS (`extract_fields`, `data_policy: local_only`). `GET /objects/<sha>/lens`
returns the job status and only the technical fields (`plate_tn, vin, date_premiere_circulation, marque,
type_commercial, genre, energie, puissance_fiscale, places_assises`) — never the holder's name, CIN or address.
IDauto stores them on the archive record as a proposal; nothing changes on the vehicle without confirmation.
